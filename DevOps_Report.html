DevOps Automation Report — ACEest Fitness

Project repository: 2025tm93233/devops-assignment-2
Report date: 25 November 2026

1. Project and CI/CD architecture

ACEest Fitness is a Python desktop application built with Tkinter. It manages fitness-club information using SQLite and includes workout, charting, and PDF-report functionality. The repository combines application source code, tests, container packaging, Jenkins automation, GitHub Actions, and Kubernetes deployment configuration.

The current delivery path has two related but distinct workflows:

  1. GitHub Actions — continuous integration and image build. A push starts the workflow in .github/workflows/ci.yml on an Ubuntu runner. It checks out the source, installs python3-tk, discovers and runs the unit tests, and then builds a Docker image.
  2. Jenkins — test, build, and deployment. The Jenkinsfile defines test and Docker-build stages, followed by a deployment stage. It selects shell commands on Unix agents and batch commands on Windows agents.
  3. Docker — packaged runtime. The Dockerfile starts from Debian Bookworm slim and installs Python, Tkinter, Matplotlib, Xvfb, and supporting packages. It installs fpdf2 in a virtual environment and launches the application under Xvfb.
  4. Kubernetes — desired deployment configuration. The manifest requests two replicas and configures rolling updates, resource requests and limits, and process-based liveness and readiness probes.

In the intended Jenkins path, a successful test stage permits the image build, which is followed by Kubernetes deployment and rollout verification. If verification fails, the pipeline requests rollback and bounded deployment cleanup.

2. Challenges and mitigation strategies

GUI dependencies in automated environments. The application uses Tkinter and Matplotlib, while CI runners and containers commonly have no graphical display. The GitHub Actions workflow installs Tkinter dependencies and executes tests without starting the GUI; the Docker image uses Xvfb for headless graphical support.

Consistent execution across Jenkins agents. Jenkins may run on either Unix or Windows. The pipeline explicitly selects sh or bat for its test, Docker, and Kubernetes commands. This improves portability but requires equivalent tools to be installed on both agent types.

Deployment failure and recovery. Applying a Kubernetes manifest does not prove that the new release becomes healthy. The Jenkins pipeline waits for rollout status with a timeout and attempts a rollback if verification fails.

Image availability and tag consistency. The two CI paths build images with different tags: GitHub Actions uses the commit SHA and latest, while Jenkins uses the Jenkins build number and latest. A shared registry and one consistent tagging strategy would make these flows interoperable.

Application and Kubernetes service model. The Docker command starts a Tkinter desktop GUI, but the Kubernetes manifest declares container port 8080 and a NodePort service. The application code should be assessed to determine whether it should run as a desktop workload, expose an HTTP interface, or use a different deployment model.

3. Key automation outcomes

  • Pushes to the GitHub repository trigger automated unit-test discovery and a Docker image build.
  • The test suite covers database initialization and selected client, workout-program, membership, and login logic.
  • Docker packages the Python runtime and the graphical/reporting dependencies needed by the application.
  • Jenkins provides a defined path from testing to image building and Kubernetes rollout, including a bounded rollout wait and rollback attempt.
  • Kubernetes configuration specifies two application replicas, rolling-update behavior, resource bounds, probes, and a NodePort service.
  • Local verification for this report: python -m unittest discover -s . -p 'test_*.py' -v completed successfully: 8 tests passed. This verifies the test suite in the local project environment.

The repository therefore demonstrates meaningful CI automation and supplies deployment building blocks. Before claiming a complete, repeatable CD release, the image publication/distribution mechanism, Kubernetes runtime environment, application network model, registry credentials, and deployment rollback configuration should be validated end-to-end.
